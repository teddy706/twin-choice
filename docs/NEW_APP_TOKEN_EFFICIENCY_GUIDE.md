# 신규 앱 개발 가이드 — 토큰 절약 체크리스트

**문서 버전:** v1.0
**작성일:** 2026-09-13
**근거**: twin-choice와 reading-buddy 두 프로젝트를 Claude Code로 실제 개발하며 겪은 사례. 각 항목에 "실제로 이런 일이 있었다"는 근거를 달았다 — 추상적 베스트 프랙티스가 아니라 관찰된 패턴이다.

> 이 문서는 **특정 앱의 문서가 아니라 다음 프로젝트를 시작할 때 그대로 복사해 갈 수 있는 메타 가이드**다. 새 저장소를 만들 때 이 파일을 그 저장소의 `docs/`(또는 루트)로 옮겨도 된다.

---

## 왜 이게 중요한가

Claude Code 세션은 매번 컨텍스트가 새로 시작된다(같은 대화 안에서도 컨텍스트 압축이 일어나고, 세션이 바뀌면 완전히 새로 시작한다). **"이미 한 번 알아낸 것을 다시 알아내는 것"이 가장 큰 토큰 낭비다.** twin-choice/reading-buddy 두 프로젝트를 나란히 개발하면서, 같은 종류의 문제(인증 구조, 음성 인식 포맷, PIN 잠금)를 한쪽에서 풀고 다른 쪽에서 또 처음부터 푸는 경우와, 이미 푼 걸 그대로 가져다 쓴 경우가 둘 다 있었다 — 후자가 압도적으로 빠르고 저렴했다.

---

## 1. 프로젝트 시작 즉시 만들 것

### 1.1 `CLAUDE.md`(또는 `AGENTS.md`) — "재논의 불필요" 표부터

가장 큰 지렛대는 **이미 확정된 결정을 다시 논의하지 않게 만드는 것**이다. twin-choice/reading-buddy 둘 다 CLAUDE.md 최상단에 이런 표를 뒀다:

```markdown
## 확정된 기술 결정 (재논의 불필요)
| 항목 | 결정 |
|---|---|
| 배포 형태 | PWA |
| 인증 — 자녀 | PIN → synthetic 계정 → 실제 Supabase Auth 세션 |
...
```

이게 없으면 매 세션 "PWA로 할까 네이티브로 할까"부터 다시 검토하려는 시도가 나올 수 있다 — 실제로 이 표가 있어서 그런 일이 한 번도 없었다.

**할 일**: 사용자와의 첫 대화(또는 PRD 논의)에서 나온 확정 사항을 이 표로 즉시 박제한다. 나중에 바뀌면 표를 갱신하되, "재검토 중"이 아닌 이상 표에 있는 건 그대로 믿고 진행한다.

### 1.2 Phase 단위로 스코프를 명시적으로 좁힌다

```markdown
**Phase 1은 완료됐고, 지금은 Phase 2를 진행 중입니다.** Phase 3, 사업화, 확장 기능은 이 시점에 손대지 마세요.
```

이 한 줄이 "이왕 하는 김에 이것도" 식의 스코프 확장(탐색성 코드 읽기, 불필요한 리팩터링 제안)을 막아준다. 번호 순서대로 진행하기로 합의하면 "앞 번호 안 끝났으면 뒷 번호 손대지 말 것"까지 명시할 것 — 실제로 이 프로젝트들에서 이 규칙 덕분에 매 세션이 좁고 예측 가능하게 유지됐다.

### 1.3 `docs/` 폴더를 처음부터 로컬 파일로 — 외부 아티팩트 링크에 의존하지 않는다

twin-choice는 초기에 PRD와 "개발 착수 전 결정 사항"을 **Claude 아티팩트 링크**로만 갖고 있었다. 나중에 이걸 로컬 `docs/PRD.md`로 옮기면서 확인해보니, 아티팩트를 `Artifact` 툴로 읽어올 때마다 실제 내용(수 KB)보다 **몇 배 큰 HTML/CSS 보일러플레이트**가 같이 딸려 왔다(스타일시트 인라인 포함). 로컬 마크다운 파일은:
- `Read` 툴로 필요한 부분만(offset/limit) 읽을 수 있다 — 아티팩트는 통째로 온다.
- git으로 버전 관리되고, 코드와 함께 diff로 리뷰된다.
- 매번 URL을 다시 안 불러도 된다.

**할 일**: PRD/설계 논의가 아티팩트나 채팅으로 오갔다면, 어느 시점(늦어도 Phase 1 끝날 때)에는 `docs/PRD.md`로 반드시 내려받아 정리한다. reading-buddy/twin-choice 둘 다 최종적으로 `docs/{PRD,BRIEF,STORIES,ARCHITECTURE}.md` 4종 구조로 수렴했다 — 처음부터 이 4개로 시작해도 된다.

### 1.4 자매 프로젝트가 있다면, 그 프로젝트의 CLAUDE.md부터 먼저 읽는다

같은 사용자가 비슷한 도메인(가족용 앱, 같은 인증 패턴)의 앱을 여러 개 만든다면, 새 프로젝트를 시작하기 전에 기존 프로젝트의 CLAUDE.md/AGENTS.md를 먼저 훑어서:
- 이미 검증된 아키텍처 패턴(예: 자녀 PIN → synthetic 계정 인증)
- "Supabase/Azure 셋업 중 발견한 함정" 같은 인프라 게이트키핑 섹션
- 재사용 가능한 코드(예: `azureSpeech.ts`, `pcmRecorder.ts`)

를 목록화해두고 시작한다. **실제 사례**: reading-buddy가 twin-choice의 인증 패턴을 그대로 가져다 썼고, 나중엔 반대로 twin-choice가 reading-buddy의 PIN 잠금/PIN 확인 버튼/Vitest 인프라/Azure Speech 코드를 그대로 가져다 썼다 — 둘 다 "이 문제를 처음부터 다시 생각하지 않고 코드를 그대로 포팅"해서 각각 한 세션 안에 끝났다. 처음부터 알았다면 그 탐색 자체(각 프로젝트가 처음 이 문제를 풀 때 겪은 시행착오)가 통째로 생략됐을 것이다.

## 2. 세션 운영 원칙

### 2.1 발견한 함정은 그 자리에서 CLAUDE.md에 기록한다 — 세션이 끝나고 나서가 아니라

두 프로젝트 다 "Supabase 셋업 중 발견한 함정", "Azure 셋업 중 발견한 함정" 같은 전용 섹션이 있다. 예:

> service_role 키는 반드시 legacy JWT 형식 — 새 형식 secret key(`sb_secret_...`)로 채우면 `admin.from(table).insert(...)` 같은 PostgREST 호출이 전부 `permission denied`로 막힌다.

이런 건 **한 번 겪으면 몇 번이고 재발할 수 있는 종류의 문제**(새 마이그레이션 추가할 때마다, 새 기능에서 admin 클라이언트 쓸 때마다)라, 처음 겪었을 때 바로 적어두지 않으면 다음에 또 같은 디버깅 비용을 치른다. 실제로 twin-choice의 AI 리소스 복구 세션에서, 조용히 삼켜지던 catch 블록 때문에 원인 진단에 여러 턴을 썼고, 그걸 고치면서 "실패는 항상 `console.error`로 로그를 남길 것"을 코딩 주의사항에 새로 추가했다 — 이 규칙이 처음부터 있었다면 그 진단 과정 자체가 훨씬 짧았을 것이다.

### 2.2 "동일하게 맞춰줘"는 정말 동일하게 — 요약하지 않는다

**실제로 겪은 실수**: 이 프로젝트에서 "AGENTS.md도 CLAUDE.md 내용에 맞춰 업데이트해줘"라는 요청을 받고, 몇몇 긴 섹션을 "같은 정보를 담되 더 간결하게" 축약해서 다시 썼다. 사용자가 diff를 확인해달라고 해서야 205줄 vs 186줄로 실제로는 여러 단락이 빠져있었다는 게 드러났고, 다시 정확한 사본으로 재작성 + 재커밋해야 했다 — 왕복이 두 배로 늘었다.

**교훈**: "동기화해줘"/"맞춰줘"/"똑같이 해줘" 류의 지시는 **정확한 사본을 의미한다고 기본 가정**할 것. "요약해도 되나?" 같은 뉘앙스가 명시적으로 없으면 임의로 편집하지 말고, 의도 파악이 안 서면 사본으로 만든 뒤 "혹시 축약본을 원하셨으면 말씀해주세요" 쪽으로 확인하는 게 재작업보다 싸다.

### 2.3 파일/디렉터리를 찾을 때 가정하지 말고 재귀적으로 확인한다

**실제로 겪은 실수**: "twin-choice엔 미들웨어가 없다"고 판단하고 넘어갔다가, 나중에 재조사해보니 `src/middleware.ts`가 실제로 존재했다 — 저장소 루트에서만 `middleware.ts`를 찾다가 `src/` 아래를 안 봤던 것. 이 착오 때문에 "인증 이중 확인 제거"라는 실제로 유효한 최적화 하나를 처음엔 "해당 없음"으로 잘못 접었다가, 나중에 다시 파고들어야 했다.

**교훈**: 파일 존재 여부를 판단할 때 `Glob`으로 `**/middleware.ts` 같은 재귀 패턴을 쓸 것 — 특정 위치 하나만 보고 "없다"고 단정하지 않는다.

### 2.4 코드 재사용 여부를 먼저 확인한 뒤에 새로 만든다

이 프로젝트들의 CLAUDE.md에는 "새 RPC/API 라우트 대신 기존 패턴 재사용", "새 테이블 없이 기존 값으로 즉석 계산" 같은 표현이 반복해서 나온다. 새 기능을 만들기 전에:
1. 이미 비슷한 걸 하는 파일이 있는지(`Grep`으로 관련 키워드 검색)
2. 자매 프로젝트에 이미 검증된 구현이 있는지
3. 새 인프라(테이블/엔드포인트/리소스)가 정말 필요한지, 아니면 기존 것 재사용/확장으로 되는지

를 먼저 확인한다. **실제 사례**: twin-choice의 AI 리소스가 삭제됐을 때, 새 Azure 리소스를 만드는 대신 reading-buddy의 기존 `gpt-4o` 배포를 그대로 재사용해서 **코드 변경 없이 환경변수만 바꿔** 복구했다. Whisper만 리전 문제로 안 됐고, 그것도 새 리전에 리소스를 새로 만드는 대신 reading-buddy가 이미 쓰던 Azure AI Speech 코드(`azureSpeech.ts`, `pcmRecorder.ts`)를 그대로 포팅해서 해결했다 — 둘 다 "새로 만들기"보다 훨씬 적은 토큰으로 끝났다.

## 3. 외부 서비스/인프라 관련 — 미리 알았으면 좋았을 것들

이 섹션은 인프라 디버깅에 특히 많은 턴을 쓰게 만드는 함정들이다(에러 메시지가 불친절하거나, 여러 서비스가 얽혀 원인 파악이 오래 걸리는 종류).

### 3.1 시크릿은 생성 즉시 별도로 백업 — Vercel의 "Sensitive" 변수는 소유자도 못 읽는다

`vercel env pull`은 "Sensitive"로 등록된 값을 `[SENSITIVE]` 플레이스홀더로만 준다 — CLI로는 어떤 방법으로도 원본을 복구할 수 없다. **실제로 이 프로젝트에서 `CHILD_AUTH_SECRET`을 이렇게 분실**해서, 이미 만들어진 모든 자녀 계정의 로그인이 끊기고 재발급 + 일부 계정 PIN 재확인까지 해야 하는 큰 작업으로 번졌다.

**할 일**: `openssl rand -hex 32` 등으로 서버 전용 시크릿을 생성하는 즉시, Vercel에 넣기 전에(또는 넣은 직후) 비밀번호 매니저나 다른 안전한 곳에 별도로 저장해둔다.

### 3.2 Azure 등 클라우드 AI 서비스는 모델별로 배포 가능 리전이 다르다

Whisper 같은 오디오 계열 모델은 텍스트/비전 모델보다 배포 가능 리전이 훨씬 좁다. 이미 만든 리소스의 리전에서 원하는 모델이 배포 목록에 안 뜨면 "리소스가 잘못됐다"가 아니라 "이 리전이 이 모델을 지원 안 한다"일 가능성을 먼저 의심한다.

### 3.3 여러 프로젝트가 같은 클라우드 구독을 쓰면 쿼터가 공유된다

같은 Azure 구독의 다른 리소스가 같은 리전에서 같은 모델의 TPM 쿼터를 이미 쓰고 있으면, 새 리소스에서 그 모델을 기본 용량으로 배포하려 할 때 실패할 수 있다. 배포 전 콘솔에서 남은 쿼터를 확인하거나 용량을 낮춰서 배포한다.

### 3.4 마이그레이션/배포 파이프라인은 "누가 언제 실행해야 하는지"를 항상 명시한다

두 프로젝트 다 마이그레이션을 `supabase db push`가 아니라 SQL Editor 수동 실행으로 적용해왔다. 새 마이그레이션을 추가할 때마다 "사용자가 SQL Editor에서 직접 실행해야 실제 DB에 반영됨"이라고 CLAUDE.md에 적어두지 않으면, 나중에 "왜 이 컬럼이 없지?"부터 다시 디버깅해야 한다(실제로 이런 이유로 배포된 사이트에서 500 에러를 만난 적 있음 — PIN 잠금 컬럼이 아직 DB에 없는 상태에서 그 컬럼을 쓰는 코드를 배포했던 것).

### 3.5 리전 불일치는 매 요청마다 누적되는 지연이다 — 처음부터 맞춰둔다

Vercel 서버 함수 리전과 DB(Supabase) 리전이 다르면, 페이지 하나가 여러 DB 호출을 하는 서버 컴포넌트에서 그 지연이 누적돼 체감 속도 저하로 나타난다. `vercel.json`에 `regions`를 DB와 같은 리전으로 처음부터 고정해둔다 — 나중에 "왜 느리지"부터 다시 원인 규명하는 것보다 훨씬 싸다.

## 4. 대화형 세션 자체를 짧게 만드는 습관

- **한 번에 하나씩, 완료 확인 후 다음.** Phase/기능 번호를 매겨 순서대로 처리하면, 세션마다 "지금 뭘 하고 있었더라"를 다시 계산하는 비용이 없다.
- **버그를 고치면서 왜 그게 버그였는지 한 줄이라도 남긴다.** "AI 실패 시 무한 스피너" 같은 근본 원인 설명이 있으면, 비슷한 패턴(예: 다른 AI 호출 지점)을 훑을 때 같은 종류의 버그를 빠르게 찾아낼 수 있다 — 실제로 이 프로젝트에서 `compare` 라우트의 버그를 고치면서 같은 패턴이 `classify-photo`/`observation-report`/`priority-suggestion` 세 곳에 더 있다는 걸 바로 알아챌 수 있었던 건, 원인을 "AI 호출에 try/catch가 없어서"로 명확히 짚었기 때문이다.
- **실제 검증(브라우저/curl/SQL)은 필요한 만큼만, 하지만 생략하지 않는다.** 검증 없이 "될 것 같다"고 넘어가면 나중에 실패를 다시 진단하는 비용이 훨씬 크다 — 반대로 이미 검증된 부분을 매번 재검증하는 것도 낭비다(예: 같은 리소스 자격 증명을 이미 curl로 확인했으면 다시 확인하지 않는다).
- **문서와 코드가 어긋나면 문서를 코드에 맞춰 갱신한다(반대 아님).** ARCHITECTURE.md 같은 "as-built" 문서는 코드가 진실이라는 원칙을 지켜야, 다음 세션이 문서를 읽고 잘못된 전제로 시작하는 걸 막는다.
