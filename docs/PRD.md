## 1. Problem Statement

일란성 쌍둥이(초등 3학년 딸)를 포함한 다태아·형제자매 가정에서, 아이들은 영상·간식·장난감 등을 고를 때 자신의 진짜 선호보다 "상대가 좋아할지"를 먼저 신경 쓰며 반복적으로 양보한다. 이 패턴이 굳어지면 (1) 부모가 각 아이의 진짜 취향과 성향을 파악하기 어려워지고, (2) 억눌린 선호가 누적되어 피로·갈등 폭발로 이어지며, (3) 장기적으로 자기 주관이 희석될 위험이 있다. 기존 가족용 의사결정 앱이나 육아 기록 앱은 "블라인드 선택 → 조율 → 성향 누적 분석"을 결합한 형태가 없어, 부모가 이 문제를 다룰 도구가 부재하다.

## 2. Goals

1. **[사용자 목표]** 아이가 상대 선택을 보기 전에 자신의 선호를 먼저 표현하는 비율을 높인다.
2. **[사용자 목표]** 불일치 상황에서 감정적 다툼 없이 조율을 완료하는 비율을 높인다.
3. **[부모 목표]** 부모가 두 아이의 카테고리별 취향 차이를 데이터로 확인할 수 있게 한다.
4. **[부모 목표]** 한쪽 아이가 지속적으로 양보하는 패턴을 조기에 감지해 알려준다.
5. **[비즈니스 목표 — V1에서는 참고용]** 실사용 데이터를 바탕으로 V2(사업화) 진행 여부를 판단할 최소 정성 근거를 확보한다.

> **[구현 노트]** 목표 4(양보 패턴 감지)는 계획보다 더 신중하게 구현됐다 — 단순 임계치 알림 대신, 최소 표본 게이트(최근 2주 4회 이상)를 넘겨야만 "AI 관찰 요약"을 사람이 직접 버튼을 눌러 볼 수 있는 형태로 바뀌었다. 자동 알림·자동 진단은 하지 않는다(진단적 언어·성격 라벨링 금지 원칙, [BRIEF.md](BRIEF.md) 7절 참고).

## 3. Non-Goals

1. **다인 형제자매(3명 이상) 지원** — V1은 쌍둥이 2인 구조에 최적화. 데이터 모델은 확장 가능하게 설계.
2. **실시간 채팅/커뮤니케이션 기능** — 아이들 간 텍스트 채팅, 부모-자녀 메시징은 포함하지 않음.
3. **AI 기반 성향 진단/성격 유형 판정 (MBTI류)** — 앱은 "행동 데이터 집계"만 하며 성격을 라벨링하지 않음.
4. **다른 가족/타인과의 데이터 공유 또는 소셜 기능** — 데이터는 해당 가족 내부에서만 접근 가능.
5. **사업화(다중 테넌트, 결제, 마케팅 사이트)** — V1은 단일 가족 사용 기준으로 설계.

## 4. User Stories

기능 단위로 분해된 최신 버전은 [STORIES.md](STORIES.md) 참고. 원본 스토리는 아래와 같다.

### 자녀 (Twin A / Twin B)
- 자녀로서, 나는 상대방이 뭘 골랐는지 모른 채 먼저 내가 좋아하는 걸 고르고 싶다.
- 자녀로서, 나는 내 선택과 상대 선택이 다를 때 놀림받지 않고 "다른 것도 멋지다"는 반응을 보고 싶다.
- 자녀로서, 나는 의견이 다를 때 정해진 방법(룰렛, 번갈아하기 등)으로 재미있게 결정하고 싶다.
- 자녀로서, 나는 실제로 고른 물건(과자, 장난감)을 사진으로 찍어서 기록에 남기고 싶다.
- 자녀로서, 나는 내 "양보 지수" 같은 분석 데이터를 보고 싶지 않다. *(비노출은 요구사항이자 안전장치)*

### 부모
- 부모로서, 나는 두 아이가 각 카테고리에서 무엇을 자주 고르는지 시간에 따라 보고 싶다.
- 부모로서, 나는 한쪽 아이가 계속 양보하고 있는지 알림으로 받고 싶다.
- 부모로서, 나는 자녀 계정을 생성·관리하고, 자녀는 볼 수 없는 대시보드에 로그인하고 싶다.
- 부모로서, 나는 자녀가 올린 선택 사진들을 카테고리별로 모아보고 싶다.
- 부모로서, 나는 카테고리와 항목 목록을 직접 추가/수정하고 싶다.

### 엣지 케이스
- 자녀로서, 내가 라운드를 시작했는데 상대가 오랫동안 응답하지 않으면, 대기를 취소하고 나중에 다시 시도하고 싶다.
- 부모로서, 사진을 업로드했는데 AI가 무엇인지 인식하지 못하면, 수동으로 카테고리/이름을 입력해 보정하고 싶다.
- 부모로서, 자녀 계정의 PIN을 잊었을 때, 부모 계정에서 PIN을 재설정하고 싶다.

## 5. Requirements

### Must-Have (P0)

**P0-1. 인증 및 역할 분리** — 부모는 이메일 회원가입/로그인, 자녀는 프로필(이름·아바타)+4자리 PIN. 자녀 세션에서는 분석/대시보드 화면 접근 자체가 DB 레벨에서 불가능해야 함.

**P0-2. 블라인드 선택 → 동시 공개 → 조율 흐름** *(기존 프로토타입에서 검증, 정식 백엔드로 이관)* — 카테고리별 항목 목록에서 선택, 상대 제출 전까지 비공개, 양측 제출 시 자동 공개, 불일치 시 조율 도구 4종(룰렛/번갈아하기/둘 다 하기/직접 정하기).

**P0-3. 사진 촬영/업로드 및 AI 자동 분류** — 촬영/업로드, AI가 카테고리·이름 자동 태깅, 인식 실패 시 수동 수정, 사람 포함 사진 안내 문구.

> **[구현 노트]** 실제로는 "고정 항목에 자동 매칭"이 아니라 **자유 라벨 방식**으로 바뀌었다 — AI가 사진을 억지로 기존 항목에 끼워맞추지 않고 짧은 한국어 라벨로 자유롭게 설명하며, "같은 걸 골랐는지"는 공개 시점에 양쪽 사진(또는 사진+라벨)을 AI가 직접 비교해서 판정한다(`rounds.ai_matched`에 캐싱). 원래 계획(체크박스 항목 매칭)보다 실제 사용 패턴에 더 맞는다고 판단해 Phase 1 중 설계를 바꿨다. 근거/상세는 [ARCHITECTURE.md](ARCHITECTURE.md) 5절.

**P0-4. 부모 대시보드 (자녀 비노출 데이터)** — 아이별·카테고리별 선호 항목 순위/추이, 양보 지수 및 임계치 알림, 사진 아카이브. 부모 역할 세션에서만 접근 가능.

> **[구현 노트]** "임계치 초과 시 자동 알림"은 하지 않기로 했다 — 대신 부모가 `/settings/dashboard`에 직접 들어가 버튼을 눌러야 AI 관찰 요약을 볼 수 있는 풀(pull) 방식으로 확정([BRIEF.md](BRIEF.md) 7절 "절대 원칙" 참고). 성격 라벨링·진단적 언어 금지 원칙이 자동 푸시 알림 방식과 충돌한다고 판단했기 때문.

**P0-5. 기록(히스토리)** — 모든 라운드 이력을 시간순 조회. 자녀 화면에서는 "무엇을 골랐는지"만, 양보 지수·통계는 제외.

> **[구현 노트]** 이 원칙에 사용자가 명시적으로 예외를 하나 뒀다 — `/history`(기록 화면 + "이번엔 누구 차례?" AI 제안)는 자녀도 볼 수 있게 확장됐다. "양보 지수 자녀 비노출"이라는 원칙과 충돌한다는 걸 사용자에게 알린 뒤 승인받은 **딱 한 번의 명시적 결정**이며, 이후 다른 통계 기능에 이 예외를 넓히는 근거로 쓰지 않기로 함.

**P0-6. 데이터/개인정보 최소 요건** — 광고·트래커 미포함, 부모의 자녀 데이터 전체 삭제 기능, 사진 비공개 스토리지.

### Nice-to-Have (P1) — 전부 Phase 2에서 구현 완료

- **P1-1. 카테고리/항목 커스터마이징** ✅
- **P1-2. 번갈아하기 로직 고도화**(카테고리별 최근 승자 이력) ✅ (Phase 1 조율 도구에 포함)
- **P1-3. 알림/푸시** ✅ (Web Push, 라운드 생성/공개 시점)
- **P1-4. 사진 기반 취향 콜라주** → 사진 아카이브(`/settings/photos`)로 구현, "무드보드 자동 생성"까지는 하지 않음
- **P1-5. 데이터 내보내기(CSV/PDF)** — 미구현, 필요성 낮다고 판단해 보류

### Future Considerations (P2)

- P2-1. 형제자매 3인 이상 확장 — 데이터 모델(`family_id` 기반)은 이미 대비됨, UI는 미구현.
- P2-2. 다중 가족 지원(사업화) — 스키마는 이미 멀티 가족 대비, 상용화 자체는 범위 밖.
- P2-3. 조부모/확장 가족 열람 권한 — 미구현.
- P2-4. 성향 리포트 자동 생성(주간/월간) → 유사 기능으로 "AI 관찰 요약"이 Phase 2에서 구현됨(자동 생성이 아니라 버튼 트리거).
- P2-5. 연인용/1인용 확장 — **명시적으로 폐기**. [부록](#9-제품-비전-확장성--v1-범위-아님-로드맵-참고용) 참고.

## 6. Success Metrics

### Leading Indicators
- 라운드 시작 후 양측 모두 블라인드 선택을 완료하는 비율
- 사진 업로드 시 AI 자동 분류 정확도(수동 수정 없이 저장된 비율)
- 불일치 발생 시 조율 완료까지 걸리는 평균 시간
- 부모의 주간 대시보드 방문 횟수

### Lagging Indicators
- 4주 시점 양보 지수 변화 추이(격차 축소 여부)
- 4주 이상 지속 사용 여부
- 부모의 정성적 피드백

> **[구현 노트]** 정량 지표를 자동 집계하는 별도 분석 파이프라인은 구현하지 않았다 — 필요 시 `resolutions`/`rounds` 테이블에서 직접 쿼리 가능(`src/lib/concessionStats.ts`가 그 계산 로직).

## 9. 제품 비전 (확장성 — V1 범위 아님, 로드맵 참고용)

**큰 그림**: 이 앱의 본질은 "쌍둥이 앱"이 아니라 "**관계 속에서 눈치 보며 자기 선호를 숨기는 패턴을 감지하는 도구**"다. 쌍둥이(자녀-자녀 관계)는 이 문제의 첫 번째, 가장 검증된 적용 사례일 뿐이다.

**탐색된 확장 후보와 폐기 사유**:
- *연인용 "블라인드 비교" 게임*: 폐기. 밸런스게임·커플퀴즈 앱들이 이미 이 메커니즘을 포화 상태로 점유.
- *연인용 "AI가 상대방 스타일 분석" 코칭*: 폐기. 기존 서비스와 컨셉 중복 + 동의 없는 프로파일링의 윤리적 리스크.
- *1인용 "관계 속 과잉적응 스트레스 감지"*: 현재 유력 후보이나 Daylio·Reflectly류 무드 트래커와의 차별화 미검증.

**다음 확장을 검토할 때의 원칙**:
1. 메커니즘을 먼저 시장에서 검증한 뒤에야 대상을 넓힌다.
2. 데이터가 "당사자 간 갈등의 무기"가 될 수 있는지 항상 먼저 점검한다.
3. 코드를 짜기 전에 최소 2주 수동 시뮬레이션으로 "기록하는 행위 자체가 자연스러운지" 검증한다.

이 섹션은 개발 범위에 영향을 주지 않는다 — CLAUDE.md에 "이 시점에 손대지 말 것"으로 명시되어 있다.

## 부록: 개발 착수 전 결정 사항

PRD의 Open Questions를 실제로 코드를 짤 수 있는 수준까지 구체화한 원본 문서(2026-09-02). 각 항목의 **추천안이 그대로 확정**됐다.

### 1. 앱 배포 형태 — PWA vs 네이티브 앱
**확정**: PWA. 가족 검증 단계라 개발 속도 우선. iOS 푸시는 "홈 화면에 추가" 안내로 대응.

### 2. 인증/역할 분리 — 실제 구현 방식
**확정**: `profiles` 테이블에 `role`(parent|child) + `family_id`. 부모는 Supabase Auth 이메일. 자녀는 PIN 검증 후 **synthetic 계정으로 실제 Supabase Auth 세션** 발급(role은 JWT 클레임이 아니라 `profiles.role` 컬럼으로 판별). 분석 테이블은 RLS로 `role='parent'`만 SELECT 가능 — 프론트엔드 라우팅 차단은 보조 수단일 뿐.

### 3. 사진 업로드 → AI 분석 파이프라인
**확정**: 서버사이드 분석(API 라우트) — 클라이언트 온디바이스 분석은 기기 성능 편차·구현 복잡도 문제로 배제. 얼굴 감지로 완전히 차단하지는 못하므로 안내 문구가 1차 방어선.

> **[구현 노트]** 원안은 "Claude API Vision"이었으나, **사용자가 Azure 비용을 직접 부담하기로 하면서 Azure OpenAI(gpt-4o/gpt-4o-mini)로 변경**됐다. 이유와 히스토리는 [ARCHITECTURE.md](ARCHITECTURE.md) "AI 통합" 절 참고.

### 4. 실시간 동기화 방식
**확정**: Supabase Realtime + 3초 폴링 폴백.

> **[구현 노트]** 원안은 "Broadcast + Presence"였으나, 실제 구현은 **Postgres Changes(`postgres_changes`) 구독**으로 확정됐다(`choices`/`resolutions` 테이블 변경 감지). 이 방식은 `supabase_realtime` publication에 테이블을 명시적으로 추가해야 동작하는데, 이걸 빠뜨려 Realtime이 처음부터 전혀 작동하지 않던 버그가 있었다(`0010_enable_realtime.sql`로 수정, [STORIES.md](STORIES.md) 참고).

### 5. 데이터 모델 초안
실제 구현된 최신 스키마는 [ARCHITECTURE.md](ARCHITECTURE.md) 4절 참고. 원안 대비 주요 확장: `photos`(자유 라벨 방식), `push_subscriptions`, `choices.reason`(음성 이유), `profiles.avatar_photo_path`/`pin_fail_count`/`pin_locked_until`.

### 6. 양보 지수 — 계산식과 알림 문구 톤
**확정**: 불일치 라운드 중 conceded로 기록된 비율. 최소 표본 5회 미만이면 지표 비노출(실제 구현은 "최근 2주 4회"로 더 촘촘한 게이트 적용). 알림 문구는 관찰+제안 톤, 단정/낙인 표현 금지 — 이 원칙은 AI 관찰 요약의 8원칙으로 발전([BRIEF.md](BRIEF.md) 7절).

### 7. 부모 동의 플로우 (최소 구현안)
**확정**: 별도의 법정대리인 동의 체크박스는 넣지 않음(가족 전용 개인 프로젝트로 범위를 좁힘). **사업화(타인에게 배포) 검토 시점에는 반드시 법률 검토를 다시 받을 것.**

### 8. 라운드 대기/타임아웃 정책
**확정**: 명시적 자동 만료 타임아웃은 구현하지 않음(원안은 24시간). 대신 대기 화면에서 언제든 "나중에 결과 볼게요"로 나갈 수 있고, 라운드는 상태를 유지한 채 남아있다.

### 확정된 결정 사항 요약
- **배포 형태**: PWA 확정.
- **API 비용**: 자동 분석이 아닌 "명시적 트리거" 방식(사진 촬영/공개 시점에만 AI 호출) — 비용 최소화. 이 원칙은 이후 AI 관찰 요약·우선순위 제안에도 동일하게 적용됨(항상 사람이 버튼을 눌러야 호출).
- **확장성**: 전 테이블 `family_id` 기반, "가족은 하나"라는 가정을 코드에 심지 않음 — 이 원칙은 지금까지 모든 마이그레이션에서 지켜지고 있다.
